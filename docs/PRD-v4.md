# Media Manager — PRD v4.0（个人云盘 + 运营服务）

> 产品方向：对标「百度网盘 + 小米相册」。把已有的 KMP 媒体客户端 + Go 后端，演进为
> 「个人自托管存储服务端 + 客户端 + 公网运营服务端 + 运营管理前端」的完整形态。
> 更新时间：2026-07-29
> 基线 commits：162（KMP Android+iOS 前端 + Go gRPC/REST 后端，单用户、真机验证通过）

---

## 1. 背景与现状

### 1.1 已有资产（V1~V3，162 commits）

| 层 | 现状 |
|---|---|
| 后端 | Go gRPC(:50051)+REST(:8080)，17 个端点：媒体列表/原图流/缩略图/视频信息/上传/删除/元数据/收藏(单个+列表+批量)/相册(CRUD+成员)/统计/健康检查。ffmpeg 视频抽帧，`http.ServeFile` Range 流式。能力用 `gateway` interface 断言渐进启用 |
| 前端 | KMP + Compose Multiplatform。三 Tab（本地相册/已上传/网盘）+ 全屏预览 + 编辑（裁剪/旋转/滤镜）+ 搜索 + Live Photo + 收藏 + 批量操作 + 系统分享。expect/actual 抽象视频/分享/触觉。Coil3 + Ktor |
| 数据存储 | 全部在 `backend/data/`：`uploads/`、`cloud-images/`、`thumbnails/`、`favorites.json`、`albums.json`。**无 DB、无索引、无用户概念** |

### 1.2 与目标的差距（要解决的核心问题）

1. **无用户/认证**：后端无账号体系，任何人连上 :8080 即可读写全部媒体。无法支撑「多设备」「个人空间」。
2. **无设备同步**：客户端只是「上传到某个地址」，没有增量同步、变更游标、冲突处理。多设备间媒体互不可见。
3. **无运营层**：客户端与服务端必须直连同一局域网或公网 IP，无中继/发现，跨网无法用。
4. **部署不友好**：`main.go` 硬编码 `./data`，无 Docker、无配置文件、无离线安装脚本。
5. **无运营前端**：没有面向运营方的注册审批、服务端监控、流量统计界面。

> PRD-v4 的全部工作就是把这 5 个缺口补上，**而不动**已经真机验证通过的媒体浏览/编辑/收藏/相册能力。

└─────────────────────────────┘      └──────────────┬──────────────┘

                                      ┌─────────────▼─────────────┐

**两条使用路径并存**（务实核心）：
- **路径 A（自托管直连）**：用户在自己 NAS/VPS 跑存储服务端，App 配地址直连。Sprint 范围内**优先做通这条**。
- **路径 B（运营中继）**：用户在运营服务端注册账号，登记自己的存储服务端；App 无公网 IP 时经运营服务端中继连接自己的存储服务端。作为**骨架**搭好，连接打通即止，不做高并发/商业化。

## 3. 模块一：存储服务端（个人自托管）

### 3.1 一键安装配置

**目标**：非技术用户能在自有 Linux 机器/NAS 上 10 分钟内跑起来。

- **docker-compose 一键**：`docker compose up -d` 起存储服务端 + 持久化卷 + 健康检查。镜像含 ffmpeg。
- **配置文件**：`config.yaml`（挂载进容器）—— 监听端口、数据目录、JWT 密钥、是否启用注册（首超管）、运营服务端地址（可选，用于注册上报）。
- **环境变量覆盖**：所有 `config.yaml` 字段可用 `MM_*` 环境变量覆盖，便于 docker-compose 注入。
- **离线脚本**（次优先）：`install.sh` 裸机 systemd 安装，仅当 Docker 不可用时提供。
- **首次启动**：服务端空库启动 → 输出/写入一个「超管令牌」用于创建首个用户；或开放一次性注册（`allow_signup: first`）。

### 3.2 用户认证

- **账号模型**：`user(id, username, password_hash, created_at, role)`。`role` ∈ `admin|user`。多用户隔离的**前提**，但 V4 不追求复杂权限，只做「每个用户只能访问自己的媒体」。
- **登录**：`POST /api/auth/login { username, password }` → `{ token, expires_at, user }`。token 为 JWT（HS256，密钥来自配置），有效期可配（默认 30 天）。
- **鉴权中间件**：除 `/api/auth/*`、`/healthz` 外，所有 `/api/*` 端点必须带 `Authorization: Bearer <token>`，中间件解析出 `user_id` 注入请求上下文。**所有现有媒体/收藏/相册端点改造为按 `user_id` 隔离**（数据目录从 `data/uploads/` → `data/users/{user_id}/uploads/`，收藏/相册 store 加 `user_id` 维度）。
- **注册**：`POST /api/auth/register`，受 `config.allow_signup` 控制（`off`/`first`/`open`）。
- **改密**：`POST /api/auth/change-password`。

### 3.3 存储抽象

把当前「直接 os.ReadDir + 文件路径硬编码」重构为**存储接口**，为后续对象存储/外挂盘留扩展点，但 V4 只实现本地文件系统一种。

```
type BlobStore interface {
    Put(ctx, userID, mediaID, reader) (size, err)
    Get(ctx, userID, mediaID) (reader, err)          // 支持 Range
    Delete(ctx, userID, mediaID) err
    Stat(ctx, userID, mediaID) (Meta, err)
}
```

- 默认实现 `LocalBlobStore`：根目录可配（默认 `data/users/{uid}/blobs/`）。
- 元数据持久化从「内存/ModTime」迁到 **SQLite**（`modernc.org/sqlite` 纯 Go 免 CGO）：`media(id, user_id, filename, type, size, mime, width, height, created_at, updated_at, sha256)`。上传即写库，删除级联清缩略图。这是性能与多用户的共同地基。

### 3.4 多设备同步 API

核心增量同步，参考百度网盘「同步盘」+ 小米「云相册自动备份」的最小可用集。

- **变更游标**：每条媒体有 `updated_at`（毫秒）。`GET /api/sync/changes?since={cursor_ms}&page=&page_size=` 返回 `{ changes: [MediaMetadata], next_cursor, has_more }`。`since` 用客户端本地已同步到的最大 `updated_at`。变更含「新增/更新」与「软删除墓碑」（`deleted` 标记 + `id`）。
- **上传带客户端指纹**：`POST /api/media/upload` 增加 `sha256`、`client_id`、`taken_at`(拍摄时间) 字段。服务端按 `(user_id, sha256)` 去重（秒传），已存在直接返回已有 `media_id`。
- **设备登记**：`POST /api/device/register { device_name, platform }` → `{ device_id }`；`GET /api/device/list` 列出该用户所有设备。用于「多设备可见性」与运营层连接管理。
- **冲突策略（V4 极简）**：媒体以 `sha256` 为内容主键，元数据（收藏/相册归属）以「最后写入为准 + 墓碑」合并。不做文件级三方合并。在 PRD 里明确：**编辑覆盖即同步，不保留历史版本**（非目标 §6.2）。

### 3.5 既有能力保留

缩略图/视频流/视频信息/收藏/相册/编辑后回传——**接口契约不变**，仅内部加 `user_id` 隔离。前端三 Tab（本地/已上传/网盘）中「已上传」即变为「本账号云上媒体」，逻辑天然复用。

## 4. 模块二：客户端核心功能

### 4.1 认证流程（新增）

- **登录页**：服务端地址 + 用户名 + 密码。地址可手动填，也可选「扫描/粘贴运营服务端提供的连接信息」自动填存储服务端地址（路径 B）。
- **会话持久化**：token 存 `SettingsStorage`（迁移到 `expect/actual` 安全存储：Android Keystore-backed `EncryptedSharedPreferences`，iOS Keychain）。
- **401 拦截**：Ktor 客户端统一拦截 401 → 清 token → 回登录页。
- **多账号/多服务端（非目标）**：V4 仅单账号单服务端，不做账号切换器。

### 4.2 自动同步（核心新增）

- **云相册自动备份**：参考小米相册「自动备份」开关。开启后，本地相册新增图片/视频**后台增量上传**（按拍摄时间过滤可选：仅 WiFi、仅充电等基础策略）。
- **增量拉取**：App 启动 + 进入「已上传」Tab 时调 `/api/sync/changes`，用本地游标拉增量，写入本地缓存索引，UI 平滑刷新。
- **去重秒传**：上传前先算 `sha256`（大文件分块哈希），命中服务端已存在则跳过字节传输。
- **冲突/离线**：弱网时上传入队本地待办表（SQLite），恢复网络后重放；拉取失败保留旧缓存可看。不做实时双向编辑同步。

### 4.3 相册浏览（保留 + 增强）

- 现有三 Tab + 预览 + 编辑 + 搜索 + Live Photo + 收藏 + 批量操作**全部保留**。
- 「已上传」Tab 升级为按 `/api/sync/changes` 维护的云端媒体视图（含已删墓碑过滤）。
- 新增「按设备/时间线」筛选（同步带来 `device_id`，可选展示来源设备）。

### 4.4 视频播放（保留）

Range 流式 + 本地文件播放**不变**，只是 stream 端点带 token。

### 4.5 文件管理（新增轻量）

- **网盘文件视图**：在「我的」Tab 下增加「文件管理」入口，列出云端所有媒体（含视频），支持：
  - 按类型/时间/大小筛选与排序
  - 批量下载到本地相册（复用现有下载流 + 写 MediaStore/相册）
  - 批量删除云端（调云删除，写墓碑）
  - 查看占用空间（服务端 `/api/sync/usage` 返回该用户总量）
- 不做目录/文件夹层级（非目标 §6.3）——媒体扁平 + 相册分组足够。

## 5. 模块三：运营服务端（公网，骨架）

> 运营方部署在公网的中心节点。职责：让客户端与服务端在跨网时能找到彼此并打通连接。**V4 只搭骨架、跑通连接**，不追求高可用/计费/多租户运营。

### 5.1 设备发现

- 客户端登录运营服务端（与存储服务端**同一套账号体系**或独立？V4 取**独立轻量账号**，运营服务端自管 `op_user`，避免与各自托管存储服务端的用户耦合）。
- 客户端上报自己绑定的 `server_id`（其存储服务端在运营服务端的注册号）。
- 运营服务端维护 `device(server_id, device_id, online, last_seen, relay_session)` 在线表。

### 5.2 连接中继

- **信号交换**：客户端与存储服务端各自与运营服务端维持 WebSocket 长连。客户端要连存储服务端时，运营服务端做「介绍」：把双方的公网/内网候选地址互换（类 ICE 信令）。
- **直连优先**：先尝试 P2P（NAT 穿透候选）；失败则走运营服务端 **TURN 式中继**转发流量。
- **V4 实现**：信令交换 + 简单 TCP 中继（运营服务端开一对 socket 双向 copy）。WebRTC 被列为非目标（§6.4），先用裸 TCP 中继跑通。

### 5.3 用户注册 / 服务端注册

- **运营账号**：`POST /op/auth/register|login`，运营服务端自管。
- **服务端注册**：存储服务端启动且配了运营服务端地址时，`POST /op/server/register { owner_op_user_id, endpoint, label }` → `{ server_id, server_token }`。之后存储服务端用 `server_token` 连运营服务端维持长连、上报心跳。
- **绑定**：用户在运营前端把自己的 `op_user` 与 `server_id` 绑定（一个用户一台自托管服务端，V4 不做多服务端）。

### 5.4 连接管理 & 流量记账

- 记录每条中继会话 `relay_session(id, server_id, device_id, start, bytes_in, bytes_out, status)`。
- `GET /op/admin/...` 供运营前端查询（见模块四）。
- 流量按 `server_id` 聚合，V4 只做计数，不做计费扣费。

## 6. 模块四：运营前端（管理界面）

> 面向运营方的 Web 管理台。技术选型务实：Go 后端内嵌静态资源 + 轻前端（HTMX 或纯 HTML+少量 JS），不开 SPA 框架，降低构建复杂度。

### 6.1 页面

| 页面 | 功能 |
|---|---|
| 登录 | 运营管理员登录 |
| 用户管理 | 运营账号列表、禁用/启用、查看绑定服务端 |
| 服务端监控 | 已注册存储服务端列表：在线状态、心跳、版本、所在地域(可选)、绑定用户 |
| 设备/连接 | 当前在线设备、活跃中继会话列表、主动断开 |
| 流量统计 | 按 server_id/日 聚合的流量图表、Top N |

### 6.2 非功能

- 嵌入运营服务端二进制，`/admin/*` 路由，独立管理员账号体系。
- 最小权限：只读看板 + 几个写操作（禁用用户、断开连接）。

---

## 6.3 非目标（明确不做，防过度设计）

1. **不保历史版本**：编辑/覆盖即最新，无版本树、无回收站多代。
2. **不做双向实时编辑协同**：同步是「增量备份 + 墓碑合并」，非 CRDT。
3. **不做文件夹层级**：媒体扁平 + 相册分组，无网盘式目录树。
4. **不上 WebRTC/P2P 复杂栈**：中继先用裸 TCP 信令+转发跑通。
5. **不做计费/套餐/多租户商业化**：流量只计数。
6. **不动已验证的媒体浏览/编辑/收藏/相册/分享核心体验**：仅加 `user_id` 隔离 wrapper，不改交互。
7. **不做账号多开/切换**：客户端单账号单服务端。

## 7. 核心可用路径（MVP 验收主线）

> 全部任务的终极验收围绕这条主线：

1. 运营方在公网机 `docker compose up` 运营服务端 + 前端，管理员登录可见空看板。
2. 用户在自有 NAS `docker compose up` 存储服务端，`config.yaml` 填运营服务端地址 → 存储服务端自动注册到运营服务端，前端可见其在线。
3. 用户在 App 登录运营账号 → 选/绑定自己的存储服务端 → App 经运营服务端信令与存储服务端建立中继连接（跨网）。
4. App 开「自动备份」→ 拍一张照 → 数秒后出现在「已上传」Tab；在第二台设备登录同一账号 → 该照片自动同步下来。
5. App「文件管理」删除该云端照片 → 两台设备均不再显示（墓碑）。
6. 全程 `go build ./...` + `assembleDebug + compileKotlinIosArm64` 通过，真机无崩溃。

## 8. 全局验收标准

1. `cd backend && go build ./...` 通过（含 storage-server 与 ops-server 两个二进制）。
2. `cd frontend && sh gradlew :composeApp:assembleDebug :composeApp:compileKotlinIosArm64` 通过。
3. `docker compose up -d` 一键起存储服务端，`/healthz` 200。
4. 未带 token 访问 `/api/media/list` → 401；带正确 token → 200 且仅返回该用户媒体。
5. 两设备同步：A 上传 → B `/api/sync/changes` 可见 → 删除 → B 收到墓碑。
6. 运营前端可登录、可见已注册服务端在线、可见中继流量计数。
7. 现有媒体浏览/编辑/收藏/相册/分享在加 auth 后真机无回归。

## 9. 与 V3 的关系

V3（doc-sprint）补齐了「小米相册级体验」缺失项（编辑完善/批量/搜索/相册/性能/后端增强/全量 QA）。V4 在此之上**加一层「云盘基础设施」**：认证、同步、运营。V3 的客户端能力是 V4 同步的「本地源」与「编辑器」，**不重写**，只接入新的 auth/sync 数据通路。
